- [x] Screen tearing (horizontal seam during on-camera motion) in the Video Feed (video_capture_mixin.py). Diagnosed with temporary in-app instrumentation (removed after the fix) that logged OBS frame arrival rate, actual canvas draw rate, and caption redraw times every 2s. Findings, in order: (1) `CAP_PROP_FPS` returns -1 for OBS Virtual Camera, so the render tick's "track OBS's reported fps" logic (item 19) silently never fired and it always ran on the 33ms fallback; (2) the old draw path (main-thread cv2.resize + PIL + new PhotoImage per frame) took 75-110ms per draw, capping real draws at ~9-12fps with uneven pacing; (3) caption redraws contend with video draws but only mildly — desync was real, not the cause; (4) the actual root cause: the 7680x4320 capture-size request (added under a "backends clamp down to the highest native mode" theory) makes MSMF *upscale* every frame to genuine 8K (~95MB each), capping delivery at ~15fps no matter what OBS's fps is set to — OBS was serving 60. The seam itself is inherent to Tk: the canvas paints via GDI, which has no frame semantics against DWM composition, so a compose mid-blit shows top-new/bottom-old — unfixable in Tk, but invisible when consecutive frames are near-identical. Fixes: request 1920x1080 at capture open (native passthrough for a 1080p OBS canvas); letterbox-resize on the capture thread before cvtColor (both release the GIL) instead of on the Tk thread; throttle worker frame *processing* to the render interval while still draining `cap.read()` at device rate, so published frames are evenly spaced; render tick skips draws when no new frame arrived (frame sequence counter) instead of redrawing stale frames; reuse one Tk PhotoImage via `paste()` per draw instead of allocating/destroying a full-canvas image object every frame (cache dropped on feed stop, since the stop path detaches the image from the canvas item). Verified by log: draws went from oscillating 8-24fps to tracking delivery 1:1, and the user confirmed the visible tearing is gone at 1080p/steady ~30fps. If tearing ever matters again (e.g. much faster motion), the real fix is rendering the output window through a vsynced GL/D3D surface (pyglet) instead of the Tk canvas — deliberately not done now.

- [x] Status: "RealtimeSTT error: [Errno 13] Permission denied: 'C:\WINDOWS\system32\realtimestt.log'" after an in-app update. User's hypothesis (per-user vs all-user install change) was investigated and ruled out — per-user install has been the case since commit 857d1a4. Actual root cause: RealtimeSTT's own library (`core/initialization.py`) opens its log via a relative path ('realtimesst.log', not something this app controls), and the updater's silent relaunch (`update_mixin.py`, via a generated batch file + `start`) could leave the relaunched process's working directory ambiguous, resolving to `C:\Windows\System32` for a non-elevated user with no write access there. Fixed with two lines of defense: `main.py`'s `__main__` block now explicitly `os.chdir()`s to the exe's own directory (or the script's directory when not frozen) before constructing `TranslationApp`, regardless of how the process was launched; the updater's generated batch file (`_launch_installer_and_exit`, update_mixin.py) also gained an explicit `cd /d "{app_dir}"` as its first real line, so `start` never depends on inherited CWD either.
